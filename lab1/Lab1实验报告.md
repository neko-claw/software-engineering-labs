## 2 待求解问题描述
本实验的核心问题可以描述为：给定一段英文文本，将其规整化为单词序列，并据此构建一个带权有向图；随后在该图结构上执行若干图算法与文本处理任务。

### 2.1 输入数据
输入是一个英文文本文件。文本中可能包含：
- 大小写字母
- 标点符号
- 空格、换行等分隔符
- 重复出现的单词与相邻单词对

程序需要先对输入文本进行预处理，将非字母字符统一视为分隔符，把所有单词转换为小写，再提取出按原顺序排列的单词序列。

### 2.2 输出数据
程序输出包括以下几类：
1. **有向图结构**：结点表示单词，边表示相邻单词的前后关系，边权表示该相邻关系在文本中出现的次数。
2. **桥接词查询结果**：对于给定单词 `word1` 和 `word2`，输出所有满足 `word1 -> bridge -> word2` 的桥接词。
3. **新文本生成结果**：对输入的一行新文本，在相邻单词之间尝试插入桥接词，生成扩展文本。
4. **最短路径结果**：给定两个单词，输出从源单词到目标单词的最短路径及路径长度。
5. **PageRank 值**：输出某个指定单词在图中的 PageRank 分数。
6. **随机游走结果**：随机从图中某一结点出发，沿有向边游走，直到遇到重复边或无后继边为止，并输出游走序列。
7. **图像文件**：将构建出的有向图渲染为 PNG 图片。

### 2.3 约束条件
- 仅处理英文单词，非字母字符全部作为分隔符。
- 单词统一转换为小写后参与计算，避免大小写造成重复结点。
- 图是**带权有向图**，边权为相邻单词关系出现次数。
- 若查询中输入的单词不在图中，应给出明确提示。
- 若两个单词之间不存在路径，也应给出明确提示。
- 随机游走需在检测到重复边时终止，避免无限循环。

### 2.4 本人理解
从本质上看，这个问题是“文本序列到图结构”的转换问题。文本中的局部相邻关系被抽象为图上的带权有向边，因此后续的桥接词、最短路径、PageRank 和随机游走都可以统一转化为图算法问题。相比直接在字符串上操作，把文本表示为图之后，程序结构更加清晰，也更适合扩展新的分析功能。

## 3 算法与数据结构设计

### 3.1 设计思路与算法流程图
本项目按照“文本预处理 → 建图 → 图上运算”的思路实现。

#### 3.1.1 根据文本生成图
1. 读取文本文件内容。
2. 将所有非字母字符替换为空格。
3. 将文本统一转换为小写。
4. 按空白切分得到单词序列。
5. 依次扫描相邻单词对 `(words[i], words[i+1])`。
6. 对每个单词建立结点；对每个相邻对建立有向边。
7. 如果边已存在，则边权加一。

可用流程描述如下：

```text
开始
  ↓
读取文本文件
  ↓
文本规范化（去标点、转小写、切词）
  ↓
得到单词序列
  ↓
遍历相邻单词对
  ↓
建立/更新有向边及权值
  ↓
生成带权有向图
  ↓
结束
```

#### 3.1.2 展示有向图
项目中使用 `GraphRenderer` 将图渲染为图片。做法是先对所有单词结点进行圆周布局，再依次绘制结点、边、箭头和边权标签，最终输出 PNG 文件。

#### 3.1.3 查询桥接词
对于输入 `word1` 和 `word2`：
1. 判断二者是否都在图中；
2. 枚举 `word1` 的所有直接后继；
3. 若某后继结点还能到达 `word2`，则该后继是桥接词；
4. 输出桥接词列表或无桥接词提示。

#### 3.1.4 根据桥接词生成新文本
1. 对输入的新文本再次做单词提取；
2. 对每一对相邻单词查询桥接词；
3. 若存在桥接词，则随机插入一个；
4. 拼接形成新文本。

#### 3.1.5 计算最短路径
项目采用 **Dijkstra 算法**：
1. 初始化源点距离为 0，其余为无穷大；
2. 使用优先队列不断取出当前距离最小的结点；
3. 枚举其出边，进行松弛操作；
4. 最后根据前驱数组回溯得到路径。

这里边权直接使用文本中相邻关系的出现次数，因此程序求得的是“边权和最小”的路径。

#### 3.1.6 计算 PageRank 值
项目实现了迭代版 PageRank：
1. 初始时所有结点均分概率；
2. 每轮迭代中，按阻尼系数 `0.85` 将每个结点的分数分配给后继；
3. 对于无出边结点，将其分数均匀分配给全图；
4. 当两轮差值足够小时停止迭代。

#### 3.1.7 随机游走
1. 随机选取一个起点；
2. 若当前结点存在出边，则随机选一条边继续前进；
3. 若下一条边已访问过，则终止；
4. 若当前结点无出边，则终止；
5. 输出游走序列，并写入文件。

### 3.2 数据结构设计
本项目的核心数据结构是带权有向图，其定义如下：

```java
private final Map<String, Map<String, Integer>> adjacency = new LinkedHashMap<>();
```

其中：
- 外层 `Map<String, Map<String, Integer>>`：键为源单词；值为其所有出边。
- 内层 `Map<String, Integer>`：键为目标单词；值为对应边权。

#### 3.2.1 有向图数据结构含义
- `addNode(String word)`：若结点不存在则创建。
- `addEdge(String from, String to)`：建立有向边，若边已存在则权值加一。
- `containsWord(String word)`：判断结点是否存在。
- `getOutgoing(String word)`：获取某结点的所有出边。
- `getWeight(String from, String to)`：获取某条边的权值。
- `size()`：图中结点总数。
- `edgeCount()`：图中不同有向边的数量。

之所以采用 `LinkedHashMap`，是因为它既能满足基于键的快速访问，又能在一定程度上保持插入顺序，便于测试和结果展示。

#### 3.2.2 其他辅助数据结构
1. **单词序列 `List<String>`**：存储文本规整化后的单词顺序，用于建图。
2. **优先队列 `PriorityQueue<PathNode>`**：用于 Dijkstra 算法中高效选取当前最短距离结点。
3. **前驱映射 `Map<String, String>`**：用于最短路径回溯。
4. **访问边集合 `Set<Edge>`**：用于随机游走中判断某条边是否已访问，避免重复。
5. **结点位置映射 `Map<String, NodePosition>`**：用于图像渲染时保存结点坐标。

### 3.3 算法时间复杂度分析
设文本规整化后共有 `n` 个单词，图中有 `V` 个结点、`E` 条边。

#### 3.3.1 文本建图
- 文本规整化与切词：`O(n)`
- 扫描相邻单词对并更新边：`O(n)`
- 总体复杂度：**O(n)**

#### 3.3.2 查询桥接词
- 枚举 `word1` 的后继，再检查是否可到达 `word2`
- 当前实现中还会遍历图中所有单词进行判断
- 复杂度近似为：**O(V)**

#### 3.3.3 根据桥接词生成新文本
- 假设输入新文本有 `k` 个单词
- 每对相邻单词都要进行一次桥接词查询
- 总体复杂度约为：**O(kV)**

#### 3.3.4 最短路径
- 使用优先队列的 Dijkstra 算法
- 时间复杂度为：**O((V + E) log V)**

#### 3.3.5 PageRank
- 每轮需要遍历所有结点及其出边
- 单轮复杂度：**O(V + E)**
- 若迭代次数为 `T`，总复杂度：**O(T(V + E))**

#### 3.3.6 随机游走
- 最坏情况下访问每条边一次后停止
- 时间复杂度：**O(E)**

#### 3.3.7 图渲染
- 结点布局：`O(V)`
- 绘制边：`O(E)`
- 绘制结点：`O(V)`
- 总体复杂度：**O(V + E)**

## 4 算法代码的生成
本项目整体采用了较明确的分层结构：
- `graph` 包负责图结构和建图；
- `util` 包负责文本规整化；
- `io` 包负责文件读取；
- `service` 包负责桥接词、最短路径、PageRank、随机游走、图渲染等业务功能；
- `app` 包提供命令行入口；
- `tests` 包提供测试。

这种结构体现了软件工程中的模块化设计思想。大模型在生成代码时，比较适合用于：
- 初步搭建类结构；
- 快速生成标准算法框架；
- 补充测试样例与异常处理逻辑。

实际落地时，仍需要根据项目真实结构进行手工整合。例如：
- 将文本预处理单独封装到 `TextNormalizer`；
- 将图构建逻辑独立到 `GraphBuilder` 和 `TextGraphService`；
- 将不同功能拆分成多个 service 类，而不是全部堆在主函数里。

从最终仓库情况看，代码组织较规范，且测试覆盖到了主要功能，说明大模型辅助更多承担了“加速编码和梳理思路”的角色，而最终正确性仍然依赖开发者自行验证。

## 8 Git操作过程
### 8.1 实验场景(1)：仓库创建与提交
典型 Git 操作流程如下：

```bash
git init
git add .
git commit -m "init lab1 project"
git branch -M main
git remote add origin <github-repo-url>
git push -u origin main
```

这些命令完成了：
1. 初始化本地仓库；
2. 将项目文件加入暂存区；
3. 进行首次提交；
4. 设置主分支；
5. 关联 GitHub 远程仓库；
6. 推送到远程仓库。

在 GitHub 页面中可以看到仓库文件、提交记录和分支信息，从而证明提交成功。

### 8.2 实验场景(2)：分支管理
典型分支管理流程如下：

```bash
git checkout -b feature/lab1-test
git add .
git commit -m "add tests for lab1"
git checkout main
git merge feature/lab1-test
git branch -d feature/lab1-test
```

以上操作体现了分支开发与合并的基本流程：
- 新建功能分支；
- 在分支上完成开发；
- 提交修改；
- 合并回主分支；
- 删除临时分支。

## 9 在IDE中使用Git Plugin
在 IntelliJ IDEA 中，可直接通过内置 Git 插件完成版本控制操作。基本步骤如下：
1. 打开项目后，IDE 自动识别 Git 仓库；
2. 在 Version Control 面板查看修改文件；
3. 选中文件后执行 Commit；
4. 填写提交说明；
5. 通过 Push 操作将提交同步到 GitHub。

相比命令行方式，IDE 图形界面更直观，适合查看差异、选择提交内容和处理简单冲突。但命令行方式更加通用，也更有利于理解 Git 的底层流程。

## 10 小结
通过本次实验，我对“文本 → 图 → 图上运算”的建模过程有了更清晰的理解。与过去单纯从零开始手写代码不同，在引入大模型辅助后，可以更快地完成以下工作：
- 梳理模块划分与类设计；
- 获取常见算法的实现框架；
- 生成较规范的样板代码；
- 快速整理测试思路和实验文档。

但与此同时，大模型也带来了额外工作：
- 需要判断其输出是否真正符合题意；
- 需要修正不严谨或不完整的部分；
- 需要通过测试验证边界情况；
- 需要对输出结果进行人工分析，而不是直接照抄。

因此，大模型更适合作为开发助手，而不是代替开发者思考。真正决定程序质量的，仍然是需求理解、数据结构设计、算法选择、测试验证和工程化组织能力。本实验让我认识到：合理使用大模型，确实能提升开发效率；但只有将其与人工分析、测试和版本管理结合起来，才能形成完整而可靠的软件工程实践流程。
